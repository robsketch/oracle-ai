## Findings

### 🟡 Hard-parse load from literal SQL (parsing)
- **Evidence:** Soft Parse % 80.57, Library Hit % 85.82, Execute to Parse % 56.45, % Non-Parse
  CPU 89.87. Hard parses 6.4/s (about 28,800 in the window) out of 32.7 parses/s. Time model:
  hard parse elapsed 21.4 s = 12.6% of DB time. Captured SQL accounts for only **5.0% of DB
  time, 5.3% of CPU and 2.9% of buffer gets**. The rest came from statements each too cheap for
  AWR's top-SQL thresholds. The captured top SQL is all Oracle housekeeping
  (`dbms_auto_report_internal`, `prvt_hdm`, `wrh$_*`, dictionary `obj$`/`hist_head$` lookups).
- **What it means:** A *hard parse* means Oracle compiles a statement and builds its plan from
  scratch. A *soft parse* reuses a cached plan from the shared pool. When an app pastes values
  into the SQL text (`WHERE id = 42`) instead of using bind variables (`WHERE id = :1`), every
  statement is new text and gets a hard parse. That burns CPU, takes shared-pool latches and
  can lead to `ORA-04031`. The many recursive dictionary lookups (`hist_head$` 24k execs,
  `obj$`, `histgrm$`) are the optimiser's work for those hard parses. This matches the
  literal-SQL step of `scripts/demo-diag-load.sh` (**known demo artefact**). Soft parse is
  only 0.57 points above the CRIT threshold.
- **Recommendation (not executed):** Rewrite the statements with bind variables.
  `cursor_sharing=FORCE` is a stop-gap only. To find the culprits, group `V$SQL` by
  `force_matching_signature` (same statement shape, different literals) in a base-views
  query.

### 🟡 Row-lock waits on dropped demo objects (probable deadlock)
- **Evidence:** `enq: TX - row lock contention`: 5 waits, 11.6 s total, **avg 2,311.99 ms**,
  6.8% of DB time (Application wait class). Segments by Row Lock Waits: two `** MISSING **`
  objects in tablespace USERS in FREEPDB1 (obj# 73436 and 73438, 2 waits each, 80% together),
  plus 1 wait on `SYS.DBMS_LOCK_ALLOCATED`.
- **What it means:** One session waited for a row another session had locked and not yet
  committed. `** MISSING **` means the object was dropped before the report ran. That matches
  `HR.DIAG_DEMO`, which `demo-diag-load.sh` drops afterwards (**known demo artefact**). I
  couldn't check the obj#→name mapping from the file. Waits of a few seconds each fit a
  deadlock: Oracle's deadlock check runs after about 3 s of waiting and then raises
  `ORA-00060` in one session (general guidance, not checked against this system). The
  `ORA-00060` itself would be in the alert log and a trace file, which are out of scope in
  file mode.
- **Recommendation (not executed):** Run `/db-diag-review days=…` in MCP mode, covering
  2026-10-07, to confirm the `ORA-00060` and pull the deadlock graph and both SQL statements.
  The application fix is to lock rows in a consistent order, or to commit sooner.

### 🔵 Row-by-row commits (commit storm), harmless at this latency
- **Evidence:** `log file sync` 3,815 waits at 1.08 ms avg (4.1 s, 2.4% of DB time). 5.3
  transactions/s with only 2,936 bytes of redo per transaction and 13 block changes per
  transaction.
- **What it means:** Each `COMMIT` waits for the log writer (LGWR) to write redo to disk. Many
  small commits give a high wait count but a low average. That's the commit-storm step of the
  demo script (**known demo artefact**). The 1 ms latency is fine.
- **Recommendation (not executed):** Batch commits in application loops. Nothing to change on
  the database side.

### 🔵 Instance lifecycle not visible here, but known
- **Evidence:** This window follows a startup at 07:35 UTC on 2026-10-07. That was before the
  `docker stop -t 120` clean-shutdown practice was verified on 2026-10-08.
- **What it means:** On this PoC, earlier startups did crash recovery because `docker stop`'s
  10 s timeout killed Oracle. They also logged ORA-00800 Set Priority Failed (no
  `--cap-add=SYS_NICE`). Both are **known, kept for demo**. AWR can't show either one, so this
  review doesn't rate them.
- **Recommendation (not executed):** Check them in an MCP-mode review if needed.

## Method

- **File mode:** `python3 -I .claude/skills/db-diag-review/extract_report.py
  reports/awr/awr_4_5.txt`. The extract (22 sections) was analysed, and I didn't read the raw
  file. The extractor found no "Top Timed Events" or "Complete List of SQL Text" section. The
  26ai report uses "Top 10 Foreground Events by Total Wait Time" instead, which I used.
- **No preflight, no MCP and no SQL** were run, as the agent instructions say for file mode.
  The database wasn't started or contacted. Reading an AWR file is always allowed under
  `LICENSING.md`. Its header shows Edition FREE anyway.
- **Choices made without asking:** (1) I rated only the five workload areas plus redo, and
  marked critical errors, incidents and lifecycle as "not assessed" rather than OK, because an
  AWR report doesn't contain the alert log. (2) I treated application errors as WARN *inferred*
  from the row-lock waits, without alert-log confirmation of `ORA-00060`. (3) I mapped the
  `** MISSING **` objects to the demo's dropped `HR.DIAG_DEMO` from the agent notes. I didn't
  check the obj# against the database. (4) Snapshot times are taken as UTC (the DB logs in UTC).
- **Caveats:** One 75-minute window from 2026-10-07, more than a week old and from an earlier
  instance startup. It isn't the current state of the database. AWR covers the whole
  instance (all containers). Top SQL captures only statements above thresholds.
- **Audit:** No MCP statements were issued in this run. In MCP mode, sessions show as
  `SQLcl-MCP` in `V$SESSION`, and the read-only `dbmon` users can't write `DBTOOLS$MCP_LOG`.
