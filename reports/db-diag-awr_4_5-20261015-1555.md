## Summary

The instance was almost idle across this 75-minute window: 0.04 average active sessions and a host that was 97.9% idle. Two things stand out. Parsing is poor: soft parse is 80.57%, only just above the CRIT line, with 6.4 hard parses/s and a library cache hit of 85.8%. That is the signature of SQL built with literals instead of bind variables. There were also 5 row-lock waits averaging **2.3 s each** (6.8% of DB time) on two objects in FREEPDB1 that no longer exist. The fix for a real system would be bind variables first, then a consistent row-locking order.

## Findings

### 🟡 Hard parsing from literal SQL (soft parse 80.57%)
- **Evidence:** Instance Efficiency: Soft Parse % 80.57, Library Hit % 85.82, Execute to Parse % 56.45. Load Profile: 32.7 parses/s, of which 6.4/s are hard. Time Model: hard parse elapsed 21.4 s (12.6% of DB time), parse time elapsed 23.3 s (13.7%). Captured SQL covers only **5.0%** of DB time and 5.3% of DB CPU, and 2.9% of the 19.7M buffer gets. So most of the work came from many small, distinct statements, each below AWR's capture threshold.
- **What it means:** A *hard parse* means Oracle compiles a statement from scratch: syntax check, optimiser and plan build. A *soft parse* reuses a plan already in the shared pool (library cache). When an application pastes values into SQL text (`... where id = 42`, then `... id = 43`) rather than using bind variables (`:id`), every statement looks new. That burns CPU, takes shared-pool latches and fragments the pool, which in the worst case leads to ORA-04031. At 80.6% this is one step from the CRIT band. It matches the literal-SQL part of `scripts/demo-diag-load.sh`, so it's **a demo artefact, deliberately induced**.
- **Recommendation (not executed):** In a real application, switch to bind variables. That is a code change: `PreparedStatement` in JDBC, or `:name` binds in PL/SQL and q-side query builders. `cursor_sharing=FORCE` is only a stop-gap. To find the culprits, group `V$SQL` by `force_matching_signature` with `count(*) > 50`.

### 🟡 Row-lock waits averaging 2.3 s on dropped demo objects
- **Evidence:** Top Foreground Events: `enq: TX - row lock contention` with 5 waits, 11.6 s total, 2,311.99 ms average, 6.8% of DB time (Application wait class). Segments by Row Lock Waits: `** MISSING **` obj# 73436 (2 waits, 40%) and obj# 73438 (2 waits, 40%), both in FREEPDB1, tablespace USERS. Also SYS.DBMS_LOCK_ALLOCATED (1 wait, 20%).
- **What it means:** A TX enqueue wait means a session wanted a row that another session had changed but not yet committed, so it had to wait. AWR shows `** MISSING **` when the object was dropped before the report ran. Two dropped USERS objects in FREEPDB1 fit `HR.DIAG_DEMO`, which `demo-diag-load.sh` creates, deadlocks on and then drops. The second object ID is probably a second demo segment, such as an index or a sibling table. I couldn't confirm that from this file. A 2.3 s average fits a deadlock: Oracle's deadlock detector takes a few seconds to notice the cycle and then rolls back one statement with ORA-00060. **Known, demo artefact.** The `DBMS_LOCK_ALLOCATED` wait is an Oracle-internal user-lock table and isn't significant.
- **Recommendation (not executed):** Confirm the deadlock with the live review (`/db-diag-review` in MCP mode), which reads the alert log for `ORA-00060` and the trace's deadlock graph. In a real app, lock rows in a consistent order, for example by primary key, and commit sooner.

### 🔵 Row-by-row commits (commit storm), low impact
- **Evidence:** `log file sync` 3,815 waits, avg 1.08 ms, 2.4% of DB time. 5.3 transactions/s, only 2,936 bytes of redo per transaction. Commit wait class 3,831 waits.
- **What it means:** Each commit waits for LGWR (the log writer) to put redo on disk. Many tiny transactions point to commit-per-row client code, which is the demo's commit-storm step. At 1 ms per write it costs little here, but on slower storage or at higher rates it becomes a bottleneck.
- **Recommendation (not executed):** Batch commits, for example every N rows or once per logical unit of work.

### 🔵 Background maintenance dominates the captured top SQL (noise)
- **Evidence:** The top captured SQL is `fhf8upax5cxsz` (`dbms_auto_report_internal.i_save_report`, 6.1 s over 15 executions), then `DBMS_REPORT`, the GV$ SQL-monitor query, `wrh$_mvparameter` (the AWR snapshot itself), `prvt_hdm` (automatic ADDM) and `DBMS_SCHEDULER`, all in CDB$ROOT or FREEPDB1 as SYS. The top parse calls are dictionary lookups (`sensitive_fixed$`, `vecsys.vector$index`).
- **What it means:** On an idle demo box, Oracle's own housekeeping fills the top-SQL lists. None of it is expensive. The demo's application SQL doesn't appear because each literal variant is too cheap to be captured (see the parsing finding). The Cartesian join on `employees` doesn't appear in the extracted top-SQL sections either. The lists were truncated, so it may have been cheap at 107 rows or fallen outside the extract.
- **Recommendation:** None. INFO only.

## Method

- **File mode:** `python3 -I .claude/skills/db-diag-review/extract_report.py reports/awr/awr_4_5.txt` (bounded extract, 22 sections found). The raw report wasn't read into context. The extractor found no section matching "Top Timed Events" or "Complete List of SQL Text". The 26ai report uses "Top 10 Foreground Events by Total Wait Time", which was used instead. The SQL lists were truncated by the extractor, so lower-ranked SQL wasn't reviewed.
- **No preflight, no MCP queries:** the agent prompt says a file path means file mode. The database wasn't touched or started for this review.
- **Licensing:** reading an AWR report file is always allowed. The header also shows Edition `FREE`, where the Diagnostics Pack is included. No ASH, ADDM or Tuning Pack was used.
- **Scope:** AWR in this CDB covers the whole instance (CDB$ROOT and FREEPDB1). The alert log, incidents, traces and lifecycle are **not assessed** and are marked ⚪ rather than guessed.
- **Assumptions (no user to ask):** (1) AWR snap times are UTC, because the DB logs in UTC. (2) The dropped objects 73436/73438 are taken to be the `HR.DIAG_DEMO` demo objects, on circumstantial evidence: FREEPDB1, USERS tablespace, `** MISSING **`, row-lock waits. Not confirmed. (3) The demo findings are rated by the normal guide and labelled as demo artefacts, not suppressed.
- **Caveats:** this is a single 75-minute window, so it's evidence, not a trend. The report filename uses host local time (BST).
- **Audit:** MCP sessions show as `SQLcl-MCP` in `V$SESSION`, and the read-only `dbmon` users can't write `DBTOOLS$MCP_LOG`. No MCP statements were issued in this file-mode run.
