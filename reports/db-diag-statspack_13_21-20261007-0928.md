## Summary

This 35-second window shows three classic application anti-patterns at once. **Hard parsing
is very high**: 254 hard parses a second, soft parse only 42.9%. That is the signature of SQL
built with literal values instead of bind variables, and the top SQL includes exactly such a
loop. **One SQL statement, a Cartesian-style join on `employees`, used 77% of all DB CPU**.
**Row locks cost 15.5% of DB time**: two waits on `enq: TX - row lock contention` of about
3 s each, which matches the two ORA-00060 deadlocks seen in the live review. There are also
about 3,000 single-row commits. The host itself was only 17% busy and I/O was negligible.
Fix the literal SQL first. Treat all ratings as evidence, not a trend, because 35 s is too
short to be one.

## Findings

### 🟡 Hard-parse storm: literal SQL instead of bind variables (CRIT pattern, short window)
- **Evidence:** Soft Parse % **42.91** (CRIT threshold < 80%). Hard parses **254.4/s**
  (8,905 in 35 s) out of 445.6 parses/s. Library Hit % 62.76, Execute to Parse % 28.08.
  `hard parse elapsed time` 3.7 s = 9.9% of DB time. Top SQL #2 (hash 1624197846, module
  SQLcl, 2.63 s CPU) is a PL/SQL loop running
  `execute immediate 'select /* diag-demo literal */ count(*) from diag_demo where id = ' || i`
  5,000 times. Each iteration is a new SQL text. Shared pool memory usage is 89–90%.
- **What it means:** Oracle has to *hard parse* (optimise and compile) every SQL text it hasn't
  seen before. A *soft parse* reuses a cached plan. Concatenating the value into the string
  makes 5,000 distinct statements, so each one is compiled from scratch and fills the shared
  pool with single-use cursors. The individual statements are cheap, so they don't appear in
  top SQL, but they show in the load profile. Sustained, this burns CPU and latches and can
  end in ORA-04031.
- **Recommendation (not executed):** Use a bind variable:
  `execute immediate 'select count(*) from diag_demo where id = :1' into n using i;`, or
  plain static SQL in PL/SQL, which binds automatically. `cursor_sharing=FORCE` is only a
  stop-gap. Re-check soft parse % over a window of 15 minutes or longer.

### 🟡 One SQL statement dominates CPU (near-Cartesian join)
- **Evidence:** Hash 3616569977, module SQLcl, 1 execution: **22.64 s CPU (76.6% of DB CPU)**,
  21.35 s elapsed (57.8% of DB time), **13.7 M buffer gets (99.3% of all gets)**, 0 physical
  reads.
  `select /* diag-demo cpu */ count(*) from employees a, employees b, employees c,
  (select level n from dual connect by level <= 200) d where a.salary + b.salary > c.salary - d.n`
- **What it means:** Three copies of `employees` (107 rows) and 200 generated rows, joined
  only on an inequality. That is about 107³ × 200 ≈ 245 M row combinations. All of it is
  logical I/O and CPU in memory. Nothing is wrong with the database. The query is the problem.
  "Buffer hit 100%" is not a sign of health here, because it hides 395k logical reads/s.
- **Recommendation (not executed):** Find the owner (module SQLcl, `diag-demo` tag; in this PoC
  it's the deliberate load script `scripts/demo-diag-load.sh`). In real life, add proper join
  predicates, or check the plan with `DBMS_XPLAN.DISPLAY_CURSOR` (free, no pack needed).

### 🟡 Row-lock contention, consistent with the ORA-00060 deadlock
- **Evidence:** `enq: TX - row lock contention` 2 waits, 6 s total, **avg 2,849 ms**, 15.5% of
  DB time. Enqueue activity: TX-Transaction 2 waits, avg 3,162 ms. `user rollbacks` 2.
  `PL/SQL lock timer` 2 × 4 s (sessions sleeping deliberately while holding locks).
  Live review: ORA-00060 at 08:17:07 (`FREE_ora_3613.trc`, HR sessions, module SQLcl), which
  is inside this window.
- **What it means:** Two sessions each locked a row and then waited for the other's row.
  After about 3 s Oracle's deadlock detector broke the cycle by rolling back one statement in
  one session (the 2 rollbacks). The wait time Statspack records is the time spent stuck before
  detection. Oracle calls this an application design problem, not a DB bug.
- **Recommendation (not executed):** Update rows in a consistent order (e.g. by primary key)
  in every code path, and keep transactions short (no sleeps or user think-time while holding
  locks). The session that gets ORA-00060 must roll back or retry.

### 🔵 Row-by-row commits
- **Evidence:** `user commits` 3,010 (86/s), transactions 86.1/s, `redo synch writes` 3,021,
  `log file sync` 3,013 waits at avg 1 ms (6.2% of DB time). Commits per transaction ≈ 1.0.
  Redo is 1,828 bytes per transaction.
- **What it means:** Each commit waits for LGWR to write redo to disk (`log file sync`). Here
  each wait is fast (1 ms), but 3,000 of them in 35 s add up. This is a client committing after
  every row.
- **Recommendation (not executed):** Commit in batches (every few hundred or thousand rows,
  or once per logical business transaction).

### 🔵 Shared pool near full
- **Evidence:** Shared pool 400 MB, memory usage 90.23% → 89.49%. Advisory: growing past
  400 MB saves nothing (Est LC time saved stays at 2,006 s), and shrinking to 384 MB costs
  little.
- **What it means:** Fullness is mostly the single-use literal cursors. More memory won't help.
  Binds will.
- **Recommendation (not executed):** No resize. Fix the literal SQL first.

statements (literal selects, single-row inserts and commits) that fall below Statspack's
capture thresholds.

## Method

- File mode: `extract_report.py` extract of `samples/statspack_13_21.txt` (15 sections found).
  I also read the Instance Activity and Enqueue Activity lines directly (user commits, parse
  counts, redo synch writes, TX/RO/CR enqueues). The raw file was not loaded in full.
- No AWR/ASH/ADDM queried or generated. No database connection used in this run.
- Caveats: **35-second window**, so ratings are softened and nothing here is a trend. Alert-log,
  incident and lifecycle areas can't be assessed from a Statspack file. The deadlock link
  comes from the earlier live MCP review, not from this file.
- Audit: no MCP session in this run. In MCP mode, statements are tagged `SQLcl-MCP` in
  `V$SESSION`, and `DBTOOLS$MCP_LOG` isn't written for the read-only `dbmon` users.
