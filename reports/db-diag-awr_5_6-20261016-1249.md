- **Evidence:** DB time 0.18 min (11.03 s) over 60.09 min elapsed. Transactions ≈ 0.0/s

### 🔵 "System I/O" wait class shows 199% of DB time
- **Evidence:** Wait Classes: System I/O 4,773 waits, 22 s, avg 4.61 ms, "199.4% DB time".
- **What it means:** System I/O waits come from background processes (control file, redo and
  datafile writes by LGWR, CKPT and DBWn). The percentage is computed against *foreground*
  DB time, which is tiny here, so it goes above 100%. It isn't a problem. A 4.6 ms average for
  background writes is fine on a WSL2/Docker laptop disk.
- **Recommendation (not executed):** none.

### 🔵 Execute-to-parse 36.5%, library hit 93.1%
- **Evidence:** Parses 11.6/s against executes 18.2/s. 41,741 parse calls. Top parsers are
  recursive internal SQL (`7qb74y7hp6cwd` auto-task settings lookup, 7,056 parses for 7,055
  execs; `SELECT :B1` from `sys$bsg_timeout`). Soft parse 96.3%.
- **What it means:** most parses are cheap *soft* parses by Oracle's own recursive code, which
  re-parses each call instead of keeping cursors open. Shared Pool Advisory shows no gain from
  a bigger pool (factor 1.0 → 2.0 saves no extra time).
- **Recommendation (not executed):** none. This is internal behaviour, not application SQL.

## Method

- **File mode:** the delegation gave a file path, so the preflight and all MCP/database steps
  were skipped. The only analysis was `python3 -I .claude/skills/db-diag-review/extract_report.py reports/awr/awr_5_6.html`,
  which detected `awr-html` and found 21 sections. Its "Top Timed Events" pattern didn't
  match, so the 26ai "Top 10 Foreground Events" section was used instead. The raw HTML wasn't
  read.
- **Licensing:** reading an existing AWR report file is always allowed. The header also shows
  Edition **FREE**, where the Diagnostics Pack is included. No ASH, ADDM or Tuning Pack calls
  were made.
- **Scope:** AWR in a CDB covers the whole instance (CDB$ROOT and FREEPDB1 SQL both appear).
- **Choices made without asking:** the alert log, ADR and lifecycle areas are rated N/A
  rather than guessed. Snapshot times are taken as UTC (the DB runs in UTC). The pair is valid
  because both snapshots belong to the same startup (07:35). The report filename uses UK
  local time (BST).
- **Caveats:** an hourly AWR window averages out short spikes. This hour was idle, so it says
  nothing about behaviour under load.
- **Audit:** no database sessions were opened for this review. In MCP mode, sessions are tagged
  `SQLcl-MCP` in `V$SESSION`, and `DBTOOLS$MCP_LOG` isn't written for the read-only `dbmon`
  users.
